引数: $ARGUMENTS

## 対応 OS バージョン

- Android 12 以降
- iOS 18 以降
- Windows 11 以降
- macOS 15 以降

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でパラメータを確定する（必須）
   - ダイアログで「調査対象の機能を入力してください」と促す（例: `ios-notification`, `windows-dialog`）
   - ダイアログで「対象OSを選択してください」と促す（ラジオボタン: Android / iOS / macOS / Windows）

3. 調査方針を固定する（必須）
   - 公式文書を最優先で調査する
   - 公式文書だけで不足する場合のみ、非公式情報（OSS, Blog, Q&A, Sample Repo など）を補助的に使用する
   - 非公式情報は「参考情報」として分離し、公式文書の内容と混同しない

4. 公式文書の調査を実施する（最優先）
   - 対象 OS の公式ドキュメント URL を列挙する
   - 対象機能に関係する API を収集し、一覧化する
   - API の責務、前提条件（権限、設定、バージョン制約）を整理する
   - API ごとに同期 / callback / async / stream・notification のどれかを公式シグネチャから判定する
   - 非同期 API は完了方式、完了スレッドまたは actor の保証、キャンセル手段、タイムアウト、リソース所有権を確認する
   - 廃止予定 API や代替 API がある場合は注記する
   - **Windows の場合は以下も必須で調査する:**
     - API が Windows App SDK に依存する場合、Package Identity（MSIX / Sparse Package / 未パッケージ）ごとの利用可否を整理する
     - 未パッケージアプリ向けのオーバーロードや代替手順があれば記載する
     - MFC DLL（`CWinApp` 継承）と C++/WinRT の共存に必要なヘッダ順序・コンパイラフラグを確認する
     - 必要な NuGet パッケージ（`Microsoft.Windows.AppSDK` 等）とバージョン要件を明記する

5. 補助調査を実施する（必要時のみ）
   - 公式文書で不足する実装パターンや落とし穴のみを補完する
   - 情報源を明示し、信頼度を `high / medium / low` で付与する
   - 公式情報と矛盾する記述は採用しない

6. API を全機能網羅で整理する（必須）
   - 対象機能をサブ機能へ分解する
   - 各サブ機能ごとに API 一覧を作る
   - 各 API に対して次を記載する:
     - API 名
     - 目的
     - 主要引数
     - 返却値またはコールバック
     - 実行方式（同期 / callback / async / stream・notification）
     - 完了スレッドまたは actor の保証（非同期の場合）
     - キャンセル手段（token / handle / task cancellation / なし）
     - エラーケース
     - 最小利用条件（OS バージョン、権限、初期化）

7. 簡単なサンプルコードを作成する（必須）
   - 各サブ機能に対して最小のサンプルコードを記載する
   - サンプルは「コピペで概念確認できる最小サイズ」を優先する
   - 1 API あたり 10〜30 行程度を目安にする
   - 擬似コードではなく、対象 OS / 言語で実行可能な構文にする
   - 対象 OS ごと使用言語:
     - Android: Kotlin
     - iOS: Swift
     - macOS: Swift
     - Windows: VC++（Visual C++）

8. 企画結果を以下フォーマットで出力する
   - 目的
   - 調査対象範囲（in / out）
   - 公式文書一覧（最優先ソース）
   - 補助ソース一覧（必要時のみ）
   - 機能マップ（サブ機能分解）
   - API 全網羅表（サブ機能別）
   - 同期・非同期 API 分類表（必須）
   - 実装リスク（権限、制約、互換性）
   - 簡単なサンプルコード集（サブ機能別）
   - Definition of Done
   - **Windows の場合は以下のセクションを追加する:**
     - プロジェクト設定要件（必要な NuGet パッケージ・コンパイラフラグ・ヘッダ追加手順）
     - Package Identity 別の対応方針（MSIX / 未パッケージ / 管理者権限実行）
     - MFC × C++/WinRT 共存時のヘッダインクルード順序と注意点

9. 企画書を保存する
   - 作成した企画結果を Markdown ファイルとして保存する
   - 保存先は `artifact/plans/<feature>/` 配下とする
   - ファイル名は `YYYY-MM-DD-<os>-<feature>-research.md` 形式を推奨する
   - 保存後に保存先パスを明示する

10. 実行確認を行う

- ユーザーに次を確認する: 「この調査結果をベースに進めますか？」
- 選択肢:
  - 実行する: 調査結果を確定、次のレビュー workflow（review-document）へ進む
  - 修正する: 指摘内容を反映して再調査・再出力
  - キャンセル: 調査結果のみで終了

11. Windows 固有の出力ルール（対象 OS が Windows の場合のみ）:

- Package Identity の制約（MSIX / 未パッケージ / 管理者権限）を実装リスク表に必ず含める
- 未パッケージアプリ向けの初期化手順（`Register(toastActivatorCLSID, launchUri)` 等）がある場合は、パッケージ済みとは別のサンプルとして提示する
- NuGet パッケージ追加手順・vcxproj への設定変更（`/std:c++17`, `/await` 等）を「プロジェクト設定要件」セクションにまとめる
- MFC + C++/WinRT の共存が必要な場合、インクルード順序の問題を「実装リスク」または「プロジェクト設定要件」に明記する
- `Setting()` プロパティによるフォールバック判定を DoD に含める（`IsSupported()` は PushNotifications 用であり混同しない）

12. 出力ルール:

- 公式文書セクションを必ず先頭に置く
- 公式と非公式の情報源を明確に分離する
- API 一覧は「抜け漏れなし」を目標にサブ機能単位で整理する
- 「同期・非同期 API 分類表」は全サブ機能を対象とし、最低限次の列を含める:
  - サブ機能 / 操作
  - システム API
  - 実行方式（同期 / callback / async / stream・notification）
  - 完了方式（戻り値 / completion / coroutine・task / event）
  - 完了スレッド・actor
  - キャンセル手段
  - リソース所有権・寿命（該当時）
- 同期・非同期が公式文書で確定できない場合は推測せず「要検証」とし、SDK header または実機確認方法を記載する
- Definition of Done に、全採用 API が同期・非同期分類表へ収録されていることを含める
- 各サブ機能に最小サンプルコードを必ず含める
- 不確実な内容は断定せず、要検証として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない
