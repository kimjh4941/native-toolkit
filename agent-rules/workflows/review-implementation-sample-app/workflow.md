引数: $ARGUMENTS

## 対応 OS バージョン

- Android 12 以降
- iOS 18 以降
- Windows 11 以降
- macOS 15 以降

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - PR番号が含まれていれば `pr=<number>` として扱う
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. レビュー対象のコードを確定する（必須）
   - `git rev-parse --abbrev-ref HEAD` を実行して現在のブランチ名を取得する
   - `git diff develop...HEAD` を実行して develop ブランチとの差分を取得する
   - 差分が空の場合はユーザーに「develop との差分がありません。ローカルの未コミット差分を対象にしますか？」と確認し、承認された場合は `git diff` を実行する
   - PR番号が `$ARGUMENTS` に含まれている場合は `gh pr view <number>` と `gh pr diff <number>` を優先して使用する

3. インタラクティブ入力で参照ファイルを確定する（必須）
   - ダイアログで「レビュー対象機能のサンプルアプリ計画ファイルを指定してください」と促す
   - 計画ファイルの入力がない場合は次を候補として提示する
     - `artifact/designs/<feature>/` 配下の `*-sample-app-design*.md`
   - ダイアログで「レビュー対象機能の実装結果ファイルを指定してください」と促す
   - 実装結果ファイルの入力がない場合は次を候補として提示する
     - `artifact/results/<feature>/` 配下の `*-sample-app-result*.md`
   - ダイアログで「対象OSを選択してください」と促す（ラジオボタン: Android / iOS / macOS / Windows）

4. プロジェクトルールを読み込む（必須）
   - `agent-rules/coding-rules/common.md` を読み込み、共通実装方針を把握する
   - 対象 OS の個別ルールファイル（`agent-rules/coding-rules/<os>.md`）を読み込む

5. 計画ファイルを読み込む（必須）
   - 指定されたサンプルアプリ計画ファイルを読み込み、次を把握する:
     - 作成・変更ファイル一覧（新規作成 / 変更 / 非変更）
     - 全セクション・全ボタンのリスト
     - 各操作の呼び出し方針とエラーハンドリング方針
     - FileProvider 等のシステム設定要件
     - 手動確認観点

6. コードレビューを実施する（必須）
   以下の観点で分析する:

   **計画書との整合性**
   - 計画書で定義した全セクション・全ボタンが実装されているか
   - 各 API の呼び出し方針が計画書と一致しているか
   - 変更ファイル一覧と実際の diff が一致しているか
   - FileProvider・Manifest 等のシステム設定が計画書どおり実装されているか
   - 手動確認観点を満たす UI が実装されているか
   - 計画書との差分（追加判断・代替手段の採用）が result ファイルの「追加判断」セクションに記録されているか

   **既存サンプルアプリのパターン準拠**
   - メインメニューからの導線（Router / MainMenu への追加）が既存パターンに沿っているか
   - サンプル画面の構成（タイトル・statusText・LazyColumn・セクションヘッダ・ボタン）が既存画面と一致しているか
   - 成功/失敗の表示文言フォーマット（✅ / ❌ / ℹ️）が統一されているか
   - スクロールコンポーネント等の共通 UI 部品の利用が既存パターンに沿っているか。既存画面のヘルパー関数が `private` 定義の場合、同パターンでの複製実装は許容する（タスクスコープを超えるリファクタリングは不要）

   **正確性**
   - ロジックの誤り、条件分岐の抜け漏れ
   - エラーハンドリングの実装漏れ（try-catch の網羅、UI への反映）
   - コールバック結果の UI 反映がメインスレッドで行われているか
   - 一時ファイル等のリソースリークがないか（try-finally / use の利用）
   - 対象 OS 固有のランタイム制約・落とし穴（`<os>.md` の該当節）を踏んでいないか。例（Windows / WinUI 3 / MSIX）: UI スレッド(STA)での非同期ブロッキング待機、パッケージ済み通知のアクティベーション登録、初期化の冪等性、非 ASCII ソースの文字コード、フォーマットログのバッファ。これらは多くがビルドでは検出されず実機実行で初めて出るため、レビューでも明示的に確認する。

   **プロジェクトルール準拠**
   - `agent-rules/coding-rules/common.md` への適合
   - 対象 OS の個別ルール（`agent-rules/coding-rules/<os>.md`）への適合
   - **サンプルアプリの依存方向**（`common.md`「サンプルアプリの依存方向」）: ネイティブサンプルがネイティブライブラリのみに依存しているか。Unity プラグインへの依存追加（ビルド設定・import）や、ライブラリを迂回したプラットフォーム API の直接呼び出しがないか。該当があれば機能側の配置不備を疑い、重大な指摘として扱う
   - Log.d がすべての対象メソッドの先頭に入っているか（android.md ルール）
   - public composable / 関数に KDoc が付いているか（android.md ルール）
   - TAG 定義が規約どおりか（クラスのフルネーム）。top-level composable は `companion object` を持てないため `private const val TAG` を package-level で定義するパターンを許容する。同一パッケージに同名の public `const val TAG` が存在する場合は画面名を含む一意の名前（例: `SHARE_TAG`）を使用することを許容する

   **コード品質**
   - 重複コードの有無（共通処理の関数化）
   - 不要な複雑さ・抽象化の過剰
   - coroutine の適切な利用（IO ディスパッチャ、メインスレッドへの切り替え）

   **セキュリティ**
   - FileProvider authority が正しく設定されているか
   - 外部からアクセスできない URI 設定になっているか（`android:exported="false"`）

7. レビュー結果を出力する（必須）
   以下の構造で出力する:

   ### レビュー概要
   - diff の変更内容のサマリーとサンプルアプリの対象機能

   ### 重大な問題（high）
   - 修正必須の問題を列挙する（なければ「なし」）

   ### 改善提案（medium）
   - 推奨する改善点を列挙する

   ### 軽微な指摘（low）
   - スタイル・命名などの軽微な指摘を列挙する

   ### 計画書整合性チェック
   - 全セクション・全ボタンの実装: ○ / △ / ×
   - API 呼び出し方針の一致: ○ / △ / ×
   - システム設定（Manifest / FileProvider 等）の正確性: ○ / △ / ×
   - 変更ファイル一覧との diff 整合: ○ / △ / ×
   - 計画書との差分（追加判断）の result ファイルへの記録: ○ / △ / ×

   ### サンプルアプリパターン適合チェック
   - メニュー導線（Router / MainMenu）: ○ / △ / ×
   - 画面構成パターン（タイトル / statusText / LazyColumn）: ○ / △ / ×
   - 成功/失敗表示フォーマット: ○ / △ / ×
   - 共通 UI 部品の利用: ○ / △ / ×

   ### プロジェクトルール適合チェック
   - common.md 準拠: ○ / △ / ×
   - <os>.md 準拠: ○ / △ / ×
   - サンプルアプリの依存方向（Unity プラグイン非依存）: ○ / △ / ×
   - Log.d 網羅性: ○ / △ / ×
   - KDoc 網羅性: ○ / △ / ×

   ### 手動確認観点の充足
   - 計画書の手動確認観点を各項目について ○ / △ / × で示す
   - △（実機未確認）は「充足」ではなく未完の open 項目として扱う。GUI / パッケージ済みアプリ（WinUI 3 / MSIX、モバイル実機）はビルド成功だけでは機能確認にならないため、実機実行で確認できていない観点を総合評価で楽観視しない。

   ### 総合評価
   - LGTM / 要修正（軽微） / 要修正（重大） のいずれかで示す
   - 実機動作確認が必須の機能（通知表示・コールバック等）が △ のまま残る場合は、その旨と残リスクを明記する

8. レビュー結果ファイルを保存する（必須）
   - 保存先: `artifact/reviews/<feature>/`
   - ファイル名: `YYYY-MM-DD-<os>-<feature>-implement-sample-app-review-vN.md`
   - 同名が存在する場合は `vN` をインクリメントし、既存ファイルを上書きしない
   - 最低限、次を含める:
     - レビュー対象（ブランチ名 / PR番号 / diff）
     - 計画ファイルのパス
     - レビュー結果（step 7 の出力全体）
     - 総合評価

9. 修正対応を確認する（必須）
   ユーザーに次を確認する:
   - 「このレビュー結果をもとに修正を行いますか？」
   - 選択肢:
     - 修正する: 指摘内容を反映して `implement-sample-app` workflow に準じて修正する
     - レビュー結果のみで終了: 修正は行わず終了する

   **止める基準（必須）**

   指摘の件数ではなく**種類**で判定する。指摘を次の 3 つに分ける。

   | 区分 | 内容 | 扱い |
   |---|---|---|
   | **A. 振る舞いを変える** | 利用者から見た動作が変わる。誤ったエラーコード、無言の失敗、クラッシュ、契約違反 | **止めない。直して再レビュー** |
   | **B. 検証手段を変える** | テストや検査の穴 | **中心契約なら直す。網羅系は記録して先へ** |
   | **C. 記述だけを変える** | 設計書・DocC・コメントの不一致 | 安ければ直す。記録して先へでも可 |

   **A が 0 になったら止める。** ただし次の 3 条件をすべて満たすこと。

   1. **レビュアーを替えて 1 回通していること。** 同一レビュアーが 3 ラウンド続けて A を
      出さなくなったら、収束ではなく視点の固着を疑う
   2. **追加した検査が、壊すと落ちることを確認済みであること。** 通ることの確認では足りない
   3. **直さない残件が、設計書に理由つきで明記されていること。** 「未実装」を通過扱いにしない

   **指摘 0 件を目標にしない。** 修正はレビュー面積を増やす（検査を足せば検査自身が対象に
   なる）ため、反復で 0 には収束しない。

   **サーキットブレーカー**（基準ではなく、立ち止まる合図）

   | 状況 | 意味 |
   |---|---|
   | 5 ラウンドを超えた | 基準そのものか、レビュー対象の切り方を疑う |
   | 同じ種類の指摘が 3 回続く | 個別の修正ではなく、それを生む仕組みを直す |

   > 根拠: macOS clipboard（NTKIT-15）で実装レビューが 12 ラウンド回った。同一レビュアーの
   > 3 ラウンドは 1H → 1H → 1H と減って収束に見えたが、レビュアーを替えた次のラウンドで
   > 4H / 7M / 7L が出て、うち 2 件は製品の実不具合だった（無言に失敗する paste button、
   > Unity への誤ったエラーコード）。件数の減少は収束ではなかった。
   > 記録: `artifact/results/clipboard/2026-09-02-macos-clipboard-implementation-feature-result-v14.md` §5

10. 出力ルール

- 指摘は具体的なファイルパスと行番号を可能な限り示す
- プロジェクトルール（common.md / <os>.md）由来の指摘は明示する
- 不確実な指摘は「要確認」として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない
