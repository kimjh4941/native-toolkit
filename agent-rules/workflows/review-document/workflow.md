引数: $ARGUMENTS

## 対応 OS バージョン

- Android 12 以降
- iOS 18 以降
- Windows 11 以降
- macOS 15 以降

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でパラメータを確定する（必須）
   - ダイアログで「レビュー対象のファイルを指定してください」と促す
   - 入力がない場合は以下の候補を提示:
     - `artifact/plans/<feature>/` 配下の `*-research*.md` を探索し、同一ドキュメントの改訂版（`-v2`, `-v3` など）がある場合は最も大きいバージョンのみ
     - `artifact/designs/<feature>/` 配下の `*-design*.md` を探索し、同一ドキュメントの改訂版（`-v2`, `-v3` など）がある場合は最も大きいバージョンのみ
     - `artifact/designs/<feature>/` 配下の `*-sample-app*.md` を探索し、同一ドキュメントの改訂版がある場合は最も大きいバージョンのみ
   - バージョンサフィックスがないファイルは `v1` とみなし、`vN` が存在する場合は `vN` を優先する
   - ユーザーが選択したファイルパスを確定する

3. 対象ファイルを読み込む（必須）
   - 指定されたファイルを読み込む
   - ファイル種別（企画書 / 設計書 / サンプルアプリ計画書）を判定する
   - ファイルサイズが大きい場合は「ファイルを読み込みました」と報告する

4. レビュー観点を設定する（必須）
   - **企画書（`*-research.md`）の場合:**
     - 公式ドキュメント参照の完全性
     - API 網羅性（抜け漏れがないか）
     - サンプルコードの実行可能性と適切性
     - リスク分析の網羅性
     - Definition of Done の明確性
   - **設計書（`*-design.md`）の場合:**
     - 企画書との整合性
     - Clean Architecture 準拠性
     - 既存実装との差分分析の正確性
     - テスト設計の網羅性
     - タスク分解の粒度と依存関係の妥当性
     - リスク緩和策の実現可能性
     - ドメインエラーの全ケース一覧が定義されているか（対象機能に対応する Error 型）
     - 各エラーの返却メッセージ/エラーコード対応表があるか、公開API返却仕様と整合しているか
   - **サンプルアプリ計画書（`*-sample-app*.md`）の場合:**
     - 設計書・実装結果との整合性（公開API・エラー契約の反映）
     - 画面要件の網羅性（機能一覧・操作導線・エラー表示）
     - 変更ファイル一覧の正確性（新規作成 / 既存変更 / 非変更の分類）
     - Android/iOS 共通実装パターンの維持（Main Menu 導線・カテゴリ別ボタン群・結果表示）
     - 既存サンプルコードとの整合性（再利用/追加/変更方針の明示）
     - 入力バリデーション方針の明示
     - 手動確認観点の網羅性

5. 別モデルにレビュー依頼を実施する（必須）
   - runSubagent を使用して別のエージェントにレビューを依頼する
   - 下記を含むレビュー指示を送る:
     - 対象ファイル内容（全文）
     - レビュー観点（Step 4 で設定したもの）
     - 対象 OS・機能情報（ファイルから自動抽出）
     - 出力形式指示: JSON 形式で以下の構造を要求
       ```json
       {
         "strengths": ["強み1", "強み2", ...],
         "improvements": [
           {
             "section": "対象セクション名",
             "issue": "問題点",
             "severity": "high|medium|low",
             "suggestion": "改善提案"
           },
           ...
         ],
         "missing_items": ["不足項目1", "不足項目2", ...],
         "overall_assessment": "総合評価（文章）"
       }
       ```

6. レビュー結果を整理・表示する（必須）
   - レビュー結果の JSON を解析する
   - 強み（strengths）を表示する
   - 改善点（improvements）を severity 順に表示する:
     - `high`: 高優先度
     - `medium`: 中優先度
     - `low`: 低優先度
   - 不足項目（missing_items）を表示する
   - 総合評価を表示する

7. レビュー結果をファイルに保存する（必須）
   - 保存先: `artifact/reviews/<feature>/YYYY-MM-DD-<os>-<feature>-<document-type>-review.md`
     - `<os>`: 対象 OS（例: `android` / `ios` / `macos` / `windows`）
     - `<feature>`: 対象ファイルのパスから自動抽出（例: `android-notification`）
     - `<document-type>`: ファイル種別に応じて `research` / `design` / `sample-app`
     - 例: `artifact/reviews/notification/2026-05-16-android-notification-research-review.md`
   - ファイル形式（Markdown）:

     ```
     # レビュー結果

     - 日付: YYYY-MM-DD
     - 対象ファイル: <レビュー対象ファイルパス>
     - 機能名: <feature>
     - 対象 OS: <ファイルから抽出>

     ---

     ## 強み

     <strengths を箇条書きで列挙>

     ## 改善点

     ### 高優先度

     <high severity の improvements>

     ### 中優先度

     <medium severity の improvements>

     ### 低優先度

     <low severity の improvements>

     ## 不足項目

     <missing_items を箇条書きで列挙>

     ## 総合評価

     <overall_assessment>
     ```

   - 保存後、保存パスを明示する

8. ユーザーに改善実施を確認する（必須）
   - 次の選択肢を提示:
     - 「改善版を自動生成する」: Step 9 へ進む
     - 「一部のみ改善する」: 改善対象を指定させる
     - 「レビュー結果のみで終了」: Step 11 へ進む

9. レビュー結果をベースに改善版を生成する（必須・選択時のみ）
   - 元ファイルを読み込む
   - レビュー結果の改善点・不足項目を統合する
   - 改善版を Markdown で生成する
   - **重要: 改善版のファイル名は別名にする**
     - 元ファイル: `YYYY-MM-DD-<os>-<feature>-research.md`
     - 改善版: `YYYY-MM-DD-<os>-<feature>-research-v2.md`（`-v2` サフィックスを追加）
     - 企画書・設計書・サンプルアプリ計画書の種別ごとに対応

10. 改善版を保存する（必須・改善実施時）

- 改善版を元ファイルと同じディレクトリに保存する
- 保存パスを明示する
- 保存後、改善版ファイルを現在の VS Code で新しいタブとして開いて表示する

11. 実行確認を行う

- ユーザーに次を確認する:
  - 改善版が出力された場合: 「この改善版をベースに進めますか？」
  - レビュー結果のみの場合: 「レビューは完了しました。」
- 改善版がある場合の選択肢:
  - 実行する: 改善版を確定
  - 修正する: 追加の修正を指定
  - キャンセル: レビュー結果のみで終了

12. 出力ルール:

- レビュー結果は構造化（強み → 改善点 → 不足項目 → 総合評価）で提示する
- severity レベルは視覚的に区別する
- 改善版が生成される場合、元ファイルと改善版の関係を明確にする（`-v2` サフィックス）
- 改善対象の詳細は箇条書き中心で書く
- 不確実な指摘は「要検証」として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない
