引数: $ARGUMENTS

## 対応 OS バージョン

- Android 12 以降
- iOS 18 以降
- Windows 11 以降
- macOS 15 以降

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でサンプル計画を確定する（必須）
   - ダイアログで「サンプルアプリ計画ファイルを指定してください」と促す
   - 入力がない場合は次を候補として提示する:
     - `artifact/designs/<feature>/` 配下の `*-sample-app-design*.md`
   - 指定された計画ファイルを読み込み、画面要件・変更ファイル一覧・実装詳細・手動確認観点を把握する

3. サンプルアプリを実装/更新する（必須）
   - 計画ファイルの実装詳細に従い、機能ごとの操作 UI を追加する
   - 入力バリデーションとエラー表示を追加する
   - 実行結果（成功/失敗）を再現可能な形で表示する
   - 既存API互換性を維持し、破壊的変更は明示承認なしで行わない

4. 検証コード/手順を追加する（必須）
   - 手動確認手順をドキュメント化する（観点・操作・期待結果）
   - 未実施ケースは理由を明記する

5. ビルド・実行確認を行う（必須）

- 対象サンプルをビルドする
- 実行可能な確認を行い、失敗時は修正する
- 実機依存で未確認の項目は明示する
- **重要: ビルド成功 ≠ 機能動作**。GUI / パッケージ済みアプリ（WinUI 3 / MSIX、Android/iOS 実機）では、コンパイル・リンクが通っても実行時に初めて出る不具合（権限・アクティベーション登録・スレッド/アパートメント制約・データバインド・初期化の冪等性・文字コードなど）が多い。CLI ビルドのみで「完了」と判断せず、step 6 の実機実行を必須工程として扱う。
- 結果記録では「ビルド確認済み」と「実機動作確認済み」を必ず区別する（混同しない）。

6. 実機確認手順を実施する（必須）

   計画ファイルの手動確認観点を実機で順に確認する。

   **インストール方法（OS別）**

   - Android: `./gradlew installDebug` を実行して接続済み実機にインストールする
   - iOS: Xcode でスキームを選択して実機に Run する
   - macOS: Xcode でスキームを選択して Run する、またはビルド成果物（.app）を直接起動する
   - Windows: プロジェクト構成に従う。
     - WinUI 3 / C++/WinRT（MSIX パッケージ済み）の場合は **Visual Studio から対象アプリを「配置(Deploy)」して F5 実行**する（CLI ビルドは MSBuild: `msbuild <proj>.vcxproj /p:Configuration=Debug /p:Platform=x64`）。MSIX のためトースト表示・コールバック・スケジュール・バッジ等は CLI 非対話では確認できず、**VS 実機実行が必須**。
     - `Package.appxmanifest`（COM/通知アクティベーション拡張など）を変更した場合は、古い登録が残ると反映されないため **クリーン配置**（対象アプリを一度アンインストール、または Clean → Deploy）してから実行する。
     - 実行中はビルド成果物（exe/dll/pdb）がロックされリンク（LNK1201 等）に失敗するため、再ビルド前にアプリを停止する。

   **確認の進め方**

   - 計画ファイルの手動確認観点を上から順に実施する
   - 各観点について「操作 → 実際の結果」を記録し、期待結果と照合する
   - 確認結果は次のいずれかで記録する:
     - 確認済み: 期待結果と一致した
     - NG（修正必要）: 期待結果と異なった。原因を特定して step 3 に戻り修正する
     - 実機未確認: 接続端末がない、OS バージョン制約など理由を明記して次へ進む
   - NG が出た場合は修正後に該当観点から再確認する

7. 実装結果を保存する（必須）

- 保存先: `artifact/results/<feature>/`
- ファイル名: `YYYY-MM-DD-<os>-<feature>-implement-sample-app-result-vN.md`
- 既存ファイルがある場合は `vN` をインクリメントし、上書きしない
- 最低限、次を記載する:
  - 変更ファイル
  - 実装したサンプル機能
  - ビルド/実行結果
  - 手動確認観点 / 未実施項目（理由付き）

8. 実行確認を行う

- ユーザーに次を確認する: 「このサンプル実装結果を採用して、次工程へ進めますか？」
- 選択肢:
  - 実行する: この実装結果を採用して review-implementation-sample-app の工程へ進む
  - 修正する: 指摘内容を反映して再実装
  - キャンセル: ここまでの修正差分は保持したまま、終了

9. 出力ルール

- 計画ファイル由来の内容と、サンプル実装時の追加判断を明確に分離する
- Android/iOS 共通実装パターンに対して、どこを維持しどこを拡張したかを明記する
- Windows/macOS 共通実装パターンに対して、どこを維持しどこを拡張したかを明記する
- 変更対象ファイルは可能な限り具体パスで示す
- テスト結果は手動確認観点と未実施項目（理由付き）を必ず示す
- 不確実な事項は断定せず、要検証として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない
