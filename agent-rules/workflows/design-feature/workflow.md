引数: $ARGUMENTS

## 対応 OS バージョン

- Android 12 以降
- iOS 18 以降
- Windows 11 以降
- macOS 15 以降

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でパラメータを確定する（必須）
   - ダイアログで「設計対象の企画書ファイルを指定してください」と促す
   - 入力がない場合は `artifact/plans/<feature>/` 配下の `*-research*.md` から候補を探索し、同一企画の改訂版（`-v2`, `-v3` など）がある場合は最も大きいバージョンのみを候補として提示する
   - バージョンサフィックスがないファイルは `v1` とみなし、`vN` が存在する場合は `vN` を優先する
   - ダイアログで「対象OSを選択してください」と促す（ラジオボタン: Android / iOS / macOS / Windows）

3. 企画書を読み込み、前提を固定する（必須）
   - 企画書から次を抽出する:
     - 目的
     - in / out スコープ
     - 機能マップ
     - API 全網羅表
     - 同期・非同期 API 分類表
     - 実装リスク
     - Definition of Done
   - 企画書に不足がある場合は「不足前提」として明記する
   - 企画書と矛盾する新要件は勝手に追加しない

4. リポジトリ実装観点で差分調査を行う（必須）
   - `agent-rules/coding-rules/common.md` を読み込み、共通実装方針を設計制約として固定する
   - 対象OSの個別ルールファイル（例: `agent-rules/coding-rules/android.md`, `agent-rules/coding-rules/ios.md`, `agent-rules/coding-rules/mac.md`, `agent-rules/coding-rules/windows.md`）を読み込み、設計制約として固定する
   - Clean Architecture の層・依存方向・Delegate 所有ルールを設計に反映する
   - **各クラスの配置モジュールを決める（必須）**: `common.md`「層とモジュールの対応」に従い、Manager 層までは必ずネイティブライブラリ側に置く。Unity プラグインに置いてよいのは Unity Bridge 層のみ
     - system Delegate / Listener の所有クラスを Unity プラグインに置いてはならない
     - 判定基準: 「Unity を使わない呼び出し元（ネイティブサンプルアプリ等）がこの機能を使う必要があるか」。必要ならネイティブライブラリ側へ置く
     - `Unity*Manager` は名前に Manager を含むが Unity Bridge 層であり、Manager 層ではない
   - TDD 方針、エラー変換方針、Unity Bridge 方針を設計に反映する
   - `common.md`「システム API に合わせた同期・非同期設計」に従い、Repository / UseCase / private helper の実行方式をシステム API に合わせる
   - Manager の公開 API 規約と下位層の実行方式を混同しない。Manager が同期 UseCase を `async` で薄く公開する場合も、Repository / UseCase を理由なく非同期化しない
   - 対象 OS の既存モジュール構成を確認する
   - 追加・変更が必要なファイル群を洗い出す
   - 既存 API / 命名規則 / ディレクトリ規約との整合性を確認する
   - 破壊的変更の有無を明記する

5. 実装設計を作成する（必須）
   - サブ機能単位で次を設計する:
     - 変更対象モジュール
     - 追加/変更 API（公開・内部）
     - データ構造
     - 制御フロー
     - 同期・非同期フロー
       - System API → Repository → UseCase → Manager callback → Manager native → Bridge の各シグネチャ
       - 完了スレッド / actor isolation
       - callback / continuation / task への変換箇所と理由
       - exactly-once、キャンセル、タイムアウト、リソース所有権（該当時）
     - エラーハンドリング
       - ドメインエラーの全ケース一覧（対象機能に対応する Error 型）
       - 各エラーの返却メッセージ/エラーコード対応表（公開API/Bridge がある場合の返却仕様）
     - 互換性方針（後方互換、段階導入）
   - 関数・型・ファイル単位まで分解する（Detailed 固定）
   - 全公開操作について「同期・非同期レイヤー対応表」を作成し、縦断する層に欠落がないことを確認する

6. テスト設計を作成する（必須）
   - 単体テスト、統合テスト、手動確認項目を分離する
   - サブ機能ごとに正常系・異常系・境界値を定義する
   - 企画書のリスク項目に対応する検証ケースを必ず含める
   - 同期 API は同期完了と不要な非同期化がないこと、非同期 API は完了 thread / actor、exactly-once、キャンセル、完了競合を検証する

7. 実装タスクへ分解する（必須）
   - 1タスクを 0.5日〜1.5日程度の粒度に分割する
   - タスクごとに依存関係、完了条件、レビュー観点を記載する
   - 先行タスク（基盤）と後続タスク（拡張）を明確に分離する
   - サンプルアプリの実装は design-sample-app で行う。サンプルアプリタスクには具体的なファイルパスを記載せず、完了条件と依存関係のみ定義する

8. 設計結果を以下フォーマットで出力する
   - 対象企画書
   - 設計目的
   - スコープ（in / out）
   - 共通実装方針の適用チェック（common.md 準拠）
   - 個別実装方針の適用チェック（対象OSルール準拠）
   - 既存実装差分サマリー
   - 実装アーキテクチャ
   - サブ機能別詳細設計
   - API 設計（公開 / 内部）
   - 同期・非同期レイヤー対応表（必須）
   - ドメインエラー一覧（全ケース）
   - エラーコード/メッセージ対応表
   - テスト設計
   - 実装タスク分解（依存関係付き）
   - リスクと緩和策
   - Definition of Done

9. 設計書を保存する
   - 作成した設計結果を Markdown ファイルとして保存する
   - 保存先は `artifact/designs/<feature>/` 配下とする
   - ファイル名は `YYYY-MM-DD-<os>-<feature>-design.md` 形式を推奨する
   - 保存後に保存先パスを明示する
   - 保存後、当該 Markdown ファイルを現在の VS Code で新しいタブとして開いて表示する

10. 実行確認を行う

- ユーザーに次を確認する: 「この設計書をベースに進めますか？」
- 選択肢:
  - 実行する: 設計書を確定、次のレビュー workflow（review-document）へ進む
  - 修正する: 指摘内容を反映して再設計・再出力
  - キャンセル: 設計書のみで終了

11. 出力ルール:

- 企画書由来の前提と新規設計判断を明確に分離する
- 共通実装方針（`agent-rules/coding-rules/common.md`）への適合可否を明記する
- 対象OSの個別実装方針（`agent-rules/coding-rules/<os>.md`）への適合可否を明記する
- サブ機能単位で抜け漏れなく設計する
- 「同期・非同期レイヤー対応表」は全公開操作を対象とし、最低限次の列を含める:
  - 操作
  - System API と実行方式
  - Repository
  - UseCase
  - Manager callback
  - Manager native
  - Bridge
  - actor / thread
  - キャンセル・リソース所有権
  - システム API と異なる方式へ変換する場合の理由
- 企画書の同期・非同期 API 分類表と設計表が一致しない場合は、差分を「新規設計判断」として理由付きで明記する
- Definition of Done に、設計表と実装予定シグネチャ・actor isolation・キャンセル契約が一致していることを含める
- 変更対象ファイルは可能な限り具体的なパスで示す
- `docs/` 配下は固定で変更対象外とし、設計対象ファイル一覧に含めない
- 不確実な事項は断定せず、要検証として明記する
- 対象機能の設計では、ドメインエラーの全ケース一覧と返却メッセージ/エラーコード対応表を必須で含める
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない
