\doxysubsection{Detailed Description}
The notification service of this process. 

Windows registers one activation handler per process, so there can be one \doxylink{class_native_toolkit_1_1_notification_1_1_manager}{Manager} at a time and a second Create fails with Not\+Supported rather than quietly taking the first one\textquotesingle{}s place. Move only, for the same reason as \doxylink{class_native_toolkit_1_1_notification_1_1_runtime}{Runtime}.

Every operation is synchronous and blocks the calling thread, including the ones the platform exposes asynchronously; that is what the implementation does today and the C++ API does not change it.

{\bfseries{Where the handler runs.}} On whichever thread the OS delivers the activation, and it is not moved to yours\+: a handler that touches UI has to marshal to the UI thread itself (NTF-\/02, RK-\/04). It is called outside the library\textquotesingle{}s own locks.

{\bfseries{The first activation can arrive before Create returns.}} When an unpackaged app is launched by clicking a toast, that activation is delivered from inside Create, on the thread calling it, exactly once (NTF-\/09). A handler must not assume the \doxylink{class_native_toolkit_1_1_notification_1_1_manager}{Manager} it was given to already exists (RK-\/10).

{\bfseries{COM.}} Create initialises COM on the calling thread as a multi-\/threaded apartment, accepts RPC\+\_\+\+E\+\_\+\+CHANGED\+\_\+\+MODE when the thread already has another apartment, and never uninitialises it (N-\/8, NTF-\/61). A thread that Create leaves as an MTA cannot then create a \doxylink{class_native_toolkit_1_1_clipboard_1_1_session}{Clipboard\+::\+Session}, which needs an STA\+: initialise the thread as an STA first if both run on it.

{\bfseries{Unpackaged apps}} get Not\+Supported from Set\+Badge, Remove\+By\+Id and Get\+All, which the platform offers to packaged apps only (NTF-\/52).
