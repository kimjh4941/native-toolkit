# 段階 0a スパイク結果: 通知とバッジを UI Automation で扱えるか

- 実施日: 2026-09-19
- 対象: `artifact/topics/windows-architecture/README.md` の段階 0a（7.2 の FlaUI と computer use の分担を確定する）
- ブランチ: `feature/NTKIT-16`
- 調査用のコード: `windows/WindowsLibraryExampleUITest/Spike/NotificationSpike.cs`（コミットしない。段階 0c で正式なテストに置き換える）

## 1. 結論

- 通知のほとんどは FlaUI で自動化できる。決め手は、数秒で消えるバナーではなく**通知センター（Win+N）から確かめる方法**だった
- バナーも、集中モード（応答不可）がオフなら FlaUI で扱える。ただしボタンは表示アニメーションが終わってから押す必要がある
- バッジは、数字なら値まで読める
- computer use に回すのは、画像の中身とバッジのグリフの種類の 2 つ
- 音声は自動テストの対象外とする

## 2. 環境

| 項目 | 内容 |
|---|---|
| OS | Windows 11 Home、ビルド 26200 |
| 表示言語 | 日本語（1041） |
| サンプルアプリ | MSIX で登録済み（Release ビルドの AppX を登録したもの） |
| テスト | .NET 10、MSTest 4.0.2、FlaUI.UIA3 5.0.0 |
| 集中モード | 普段はオン。バナーの確認のときだけテストの中でオフにし、終わったらオンに戻した（戻ったことを読み取りで確認済み） |

## 3. 項目ごとの結果

| 項目 | 手段 | 確かめ方 | 結果 |
|---|---|---|---|
| タイトル・本文 | FlaUI | 通知センターのアプリのグループ → 通知 → `Title` / `Content` | 読めた |
| ボタン → コールバック | FlaUI | 通知センターで通知を展開 → `VerbButton` を押す → サンプルの表示 | `{"action":"open"}` が届いた |
| 入力欄・選択肢 | FlaUI | 入力欄に `SetValue`、選択肢を `Select`、`Send` を押す | `{"action":"send","opt":"free","reply":"spike-reply"}` が届いた |
| 進捗 | FlaUI | 進捗バー（`progressBar`）の `RangeValue` | 30 → 60 に変わった。状態の文字（`Downloading`、`30%`）は通知の名前に含まれる |
| スケジュール | FlaUI | 予約して待ち、通知センターで探す | 3 秒後には無く、75 秒後にあった |
| 有効期限 | FlaUI（API で判定） | `GetAllNotifications` | 16 秒後に API は「無し」を返した。**通知センターにはまだ表示されていた**ので、判定には API を使う |
| バナーの表示 | FlaUI | 「新しい通知」ウィンドウの中のトースト | 0.4〜0.8 秒で現れ、約 7 秒で消えた |
| バナーのボタン → コールバック | FlaUI | バナーの `VerbButton` を押す | 現れた直後に押すと届かない。1.5 秒待ってから押すと届いた |
| バッジ（数字） | FlaUI | タスクバーのアプリのボタンの子要素 `BadgeText` | `5` が読めた。クリアすると要素が無くなる |
| `GetAllNotifications` | FlaUI | サンプルの表示 | 件数と ID が読めた |
| 画像の中身 | **computer use** | — | 画像の要素（`Image`）があることは分かるが、どの画像かは分からない |
| バッジのグリフの種類 | **computer use** | — | `BadgeText` はあるが名前が空で、alert などの種類は分からない |
| 音声 | **対象外** | — | UI Automation でも computer use でも確かめられない。音声の指定を正しく渡していることは、ライブラリのユニットテストで確かめる |

## 4. 見つけ方

### 4.1 通知センター

| 対象 | 見つけ方 |
|---|---|
| 開く | Win+N |
| ウィンドウ | クラス名 `Windows.UI.Core.CoreWindow`、プロセス `ShellExperienceHost`。**名前では探さない**（「通知センター」と「Windows シェル エクスペリエンス ホスト」の 2 通りがあった） |
| アプリのグループ | `Group` のうち、子の `Title` の名前がアプリの表示名 `Native Toolkit Example` のもの |

| 画像 | `Image`（名前も ID も空） |

## 5. 待ち時間

| 事象 | 実測 |
|---|---|
| Win+N を押してから通知が見つかるまで | 0.4〜1.5 秒 |
| 表示の API を呼んでからバナーが見つかるまで | 0.35〜0.8 秒 |
| バナーが自動で消えるまで | 約 7 秒 |
| バナーのボタンを押せるようになるまで | 1.5 秒待てば押せた。現れた直後（0.35 秒）では、Invoke でもマウスクリックでも押したことにならなかった |
| スケジュール通知 | サンプルのボタンは 60 秒後に予約する。確かめるのに 60 秒以上かかる |

## 6. 注意点

- **表示言語に依存しない**: 通知の名前には「受信日時」や「からの通知」などの日本語が入る。探すときは AutomationId（`Title` など）とアプリの表示名を使う
- **他のアプリの通知を記録しない**: 通知センターにもバナーにも他のアプリの通知が並ぶ。書き出しもスクリーンショットも、サンプルアプリのグループやトーストだけに限る。1 回目の書き出しに他のアプリの通知が入ってしまったので、そのファイルは削除した
- **集中モード**: オンだとバナーは出ない。通知センターは集中モードに関係なく使える
- **同じタグの通知は置き換わる**: サンプルの `ShowWithImage` / `ShowWithAudio` / `ShowWithExpiration` などはタグがすべて `sample` なので、続けて出すと前の通知が置き換わる。テストでは 1 件ずつ確かめる
- **Win+N は切り替え**: 通知センターが開いているときに押すと閉じる。開く前に閉じていることを確かめる

## 7. 調査の経緯

| 回 | やり方 | 結果 |
|---|---|---|
| 1 | 表示の前後で増えたトップレベルウィンドウを探す | 見つからなかった。15 秒待ってから文字で探したので、その時点ではバナーは消えていた |
| 2 | 押した直後から、すべてのトップレベルウィンドウを文字で探す | 見つからなかった。`GetAllNotifications` は 1 件を返したので、通知は届いていてバナーだけが出ていないと分かった |
| 3 | 通知センターを開いて探す | 見つかった。展開するとボタンが現れ、押すとコールバックが届いた |
| 4 | 集中モードの状態を読む | オンだった。バナーが出なかった原因 |
| 5 | 集中モードを一時的にオフにしてバナーを探す | 見つかった。ボタンは現れた直後に押すと届かず、1.5 秒待つと届いた |

## 8. UI テストの設計書で決めること

- **集中モードの扱い**: テストが集中モードを自分で切り替えて最後に戻すか、オンなら分かりやすいメッセージで失敗させるか。切り替える方式は動くことを確認したが、テストが途中で強制終了されるとオフのまま残る
- **バナーのボタンを押すまでの待ち方**: 固定の 1.5 秒ではなく、ボタンの位置が動かなくなるまで待つなど
- **スケジュール通知の待ち時間**: 60 秒待つのは遅い。数秒後に予約するボタンをサンプルに足すか（段階 0b）
- **有効期限の判定**: 通知センターの表示ではなく `GetAllNotifications` で判定する
- **computer use の確認手順書**: 画像の中身、バッジのグリフの種類
