## 3. 載せ替えの範囲（T-14）

| 機能 | C++ API へ | 内部入口に残した | 残した理由 |
|---|---|---|---|
| Dialog | 0 / 6 | 6 | 生の `MB_*` フラグ語と、埋め込み NUL を含むフィルター文字列 + 呼び出し側バッファ。設計書 S-3 が「ブリッジが内部層を直接呼ぶ逃げ道」として想定している形そのもの |
| Notification | 14 / 15 | `getAllNotifications` | 出力の JSON を backend 自身が書いている。C++ API を経由すると JSON→値→JSON の往復になり、得るものが無い |
| Bootstrap | 1 / 1 | — | `Runtime` のトークンを意図的にリークさせ、後始末しない今の振る舞い（N-7）を保つ |
| Clipboard | 20 / 27 | `reserveDeferredFormats`、履歴 6 関数 | 前者は 2 相の provider と `void*`（入力一覧 4 章の 11 番）。後者は完了の JSON を配送経路が書いており、T-12 が「手を入れない」とした経路を跨ぐ |

「残した」関数も、実装は 1 本である。C++ API と C ABI が同じ内部層を呼んでおり、同じ処理が 2 箇所に書かれている状態ではない。

## 4. 入力一覧の再検証（T-17）で見つかったこと

**読みではなく実装から導出した**ことで、次が見つかった。いずれも載せ替えの前に見つかったため、振る舞いを変えずに済んだ。

1. **通知の JSON では「キーが有って空」が「キーが無い」と 10 箇所で異なる**。実装が `HasKey` で分岐するためで、入力一覧はこの軸を持っていなかった。`NotificationContent` の 11 フィールドを `optional` にして区別できるようにした（入力一覧 1.10、4 章 16 番）
2. **予測が外れた 2 件**: combo box の空の `title` と `defaultSelection` は、コードを読む限り属性が出るはずだが、実際には App SDK の builder が空値を落とすため省略時と同じ出力になる
3. **C++ API が C ABI より厳しくなっていた 1 件**: `hasClipboardFormat(L"")` は C ABI ではエラーではなく「無い」。T-10 で書いた `Session::HasFormat` は空名を `InvalidParameter` で弾いていた。プラットフォームに無い検証を API が持つべきではないため、外した
4. **順序が観測できる 1 件**: 壊れた JSON を「通知が無効な状態で」送ると `INVALID_PAYLOAD` ではなく `DISABLED` が返る。解析より前に設定を確認していたためで、ブリッジはこの順序を再現する

## 5. 載せ替えで直した欠陥

| 欠陥 | 影響 | 対処 |
|---|---|---|
| `Manager` の操作が所有権を見ていなかった | ムーブ済みのハンドルが、生きている側の通知状態に作用する | 12 操作すべてに所有権のガードを入れた（`Session` と揃えた） |
| `__declspec(dllexport)` が残っていた（設計書 7.6.1 項目 3、T-02 の積み残し） | 静的コアから C ABI の宣言が `dllimport` に見える | 4 ヘッダーから外し、輸出面を `.def` だけにした |

## 6. 教訓

- **載せ替えの前に、今の答えを C ABI から固定する**。通知では 14 件中 2 件、Clipboard では 20 件中 2 件、読みによる予測が外れた。固定せずに載せ替えていれば、少なくとも `hasClipboardFormat(L"")` の変更は気づかれずに入っていた
- **依存の順序を飛ばさない**。設計書は T-14 を T-17 に依存させていた。飛ばして T-14 に入り、途中で「空と不在の区別」に行き当たって T-17 に戻った。最初から T-17 を先にしていれば、`optional` にするフィールドを一度で決められた
