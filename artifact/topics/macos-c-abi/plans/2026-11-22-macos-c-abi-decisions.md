## 8.1 決めること

**決定（2026-11-22、利用者）: D-21 を除き、下の推奨のとおり。D-21 は利用者の案（D）**。条件付きの 5 つ（D-4・D-6・D-7・D-8・D-24）は、1a-前の結果で推奨が変わったら利用者に決め直してもらう。D-23 は D-21 の D に合わせて `device-testing.md` に書く（許可なしにできる VM は 15.8.3 の VM だけ）。

## 8.4 決めないこと

- SwiftPM の URL や CocoaPods での公開（D-17 の C）。別のトピック
- Unity 向けの `.bundle` の配布物（D-24 の B）。要る利用者が出たら足す
- `MacLibrary` にあってブリッジに無い機能の C ABI（D-5 の B）
- macOS の CI。Windows の段階 7 と同じく、別に行う
- コマンドラインのツール、デーモン、App Extension からの利用（通知の関数は落とさずにエラーで返すことだけを約束する）
- Developer ID での署名と公証の確かめ（Apple Developer Program の登録が要る。D-18）
- Mac App Store の審査に出すこと（sandbox で動くことは smoke とサンプルで確かめる）
- Flutter・Rust・Godot での動作の確認。2.0.0 で確かめる利用者は Unity（1a と 2c）と smoke の C / Objective-C のアプリだけで、ほかはマニュアルに「確かめていない」と書く
- Unity のエディターの中でネイティブを呼ぶこと（今の C# はエディターで呼ばない。変えるなら `unity-native-plugin` の課題）
- 機能ごとの配布物（`feature-split-distribution`）。全 OS の C ABI の後に決める。ただし C の入口とヘッダーは機能ごとに分けておく
- Swift の土台の本当の共通化（D-1 の B）。`feature-split-distribution` で配布物の形と一緒に決める
