## 2 回目の区分 A の確認

Claude は、登録の状態の表（5.7）を、off-main の登録の直後の完了、off-main の取り消しと main の完了の重なり（3 通り）、コールバックの中の解除、同じ回の登録と解除、受け付けの失敗の順で追い、どれも完了 1 回・`release` 1 回で、main を待つことも落ちることも無いと確かめた。初期化の表も、待ち合いと入り直しは起きない（`JNI_OnLoad` どうしは `Runtime.loadLibrary0` の同期で順に動く）。

一部だけのものは、下の新しい A に含まれる。

## 区分 A（新規）

| ID | 問題 | 出典 | 対処（第 4 版） |
|---|---|---|---|
| T-X1、T-C1 | `ensureInitialized` の CAS に負けた側が「済んだ」と「途中」を区別できず、Kotlin の側が済む前に `READY` が立ちうる。逆に `IN_PROGRESS` を返し続けうる | 両方 | Kotlin の側を 3 値（未着手・途中・済み）にし、`READY` は C の表と Kotlin の側の両方が済んだ後、後に済んだ側が CAS で立てる（5.3） |
| T-X2、T-C2 | やり直しの約束が閉じていない。Kotlin の `init` の UNINIT の枝は、C に入る口が無いので実行できない | 両方 | やり直せる結果（`IN_PROGRESS`、`JNI_FAILURE`）とやり直せない結果（`CLASS_NOT_FOUND`）を決めた。Kotlin の `init` は `InitResult` を返し、表が作れないときは `NATIVE_SETUP_REQUIRED`（1.4、5.3） |
| T-X3、T-C3 | Share の選ばれたアプリが README 6 章では完了の扱い。全登録へ配ると、どの Share の結果か対応付けられない | 両方 | イベントに要求の ID を付ける。届くのは直前の Share の選択だけ（今と同じ）。README 6 章の分類を直した（AC-22、5.8） |
| T-X5 | K-4（前の待ちを消さない）が 1b の「動作を変えない」と食い違う | Codex | K-4 を取り下げ、今の振る舞いのままにした（AC-22、K-4） |
| T-X4 | 足す・外す形のイベントの登録は、今の差し替え型の `set*Listener` と意味が違い、Unity の移行で差し替えを保つ条件が無い | Codex | AC-23 の原則と C-6（Unity の包みが種類ごとに 1 つのハンドルを持ち、外してから足す） |
| T-X6、T-X7 | 設定の画面と Share に足した前面の判定が、今のブリッジ（前面を確かめず、Activity でなければ `NEW_TASK`）と違う | Codex | AC-23 の原則。違いを 5.8 に書き、第 2 部の対応表の列に「違いと理由」を持たせた |
| T-C4 | 完了つきの操作の取り消しを何で指すかと、完了の後の取り消しの扱いが無い | Claude | 使い回さない 64 ビットの要求の ID で取り消す。完了の後と知らない ID は何もしない。一括の取り消しは作らない（1.3.1、5.7） |

**仕組みの修正**: 今のブリッジとの互換の指摘が 2 回目から続いたので、AC-23（C ABI はブリッジを写さず、README 6 章の振る舞いの集合を満たす。違いは第 2 部の対応表に書き、Unity から見た動作は 2c の包みが保つ）を決めた。根拠は、利用者の決定（2026-10-03）「Unity は C ABI を呼ぶので、Unity の側をそれに合わせて変える」。

## 総合評価

登録の状態の表は 3 回目で崩れなくなった。新しい A は 11 件（Claude 4、Codex 7。重なりを除くと 4 つの塊）で、初期化の表の細部と、今のブリッジとの互換に集まった。第 4 版で反映し、互換については原則（AC-23）を決めた。4 回目のレビューで A が 0 になったかを確かめる。
