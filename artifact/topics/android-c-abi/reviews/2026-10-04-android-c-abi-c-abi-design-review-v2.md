## 区分 A（新規）

| ID | 問題 | 出典 | 対処（第 3 版） |
|---|---|---|---|
| S-C1 | off-main の登録で、C が「有効」にする前に main が挿入と配送を処理しうる。すぐ決まる完了と保っていたイベントが黙って抜ける | Claude | C は登録を `ACTIVE` で作ってから受け口を呼ぶ。挿入と操作の開始を 1 つの main のメッセージにする。off-main から呼んだときは戻る前に完了が来うる、を契約にした（1.3、5.7） |
| S-C2 | 挿入と「外す」の両方が `release` を呼ぶので 2 回になる | Claude | `release` は状態を `RELEASED` に CAS できた 1 か所だけ。挿入は解除の要求を見たら何もしない（5.7 の表） |
| S-C3 | ライブラリの側で終わる登録（差し替え、close、置き換え、取り消し）の契約が無い | Claude | イベントの登録はライブラリの側で終わらせない。完了つきの操作はハンドルを持たず、ライブラリの側で終わるときも必ず完了する（AC-21、5.7） |
| S-C4 | Share の結果は閉じたときに何も来ないので、完了にできない | Claude | 「選ばれたアプリ」はイベントの登録にし、開く操作の完了は開けたかどうかまで（AC-22） |
| S-X1 | ちょうど 1 回の完了の対象が狭い（K-3） | Codex | README 6 章の「操作の完了」のすべてと権限の要求に広げた（1.3、K-3） |
| S-C5 | 初期化の中間の状態が無く、`READY` を立てる時点が無い | Claude | `UNINIT` → `NATIVE_READY` → `READY`（と `FAILED`）の状態と出来事の表（5.3） |
| S-C6 | 準備のミューテックスを持ったまま Java を呼ぶので、`dlopen` の経路での入り直しと、起動中の main とのデッドロックが起きる | Claude | ミューテックスは C の表づくりだけ。どの経路も待たない（`try_lock`、`IN_PROGRESS`）。手動の経路は `System.loadLibrary` も `AppInitializer` も呼ばない（5.3、AC-16、K-8） |
| S-C7 | `JNI_OnLoad` の失敗で `FAILED` に固まる | Claude | `FAILED` はアプリのクラスローダーを持つ経路の失敗だけ（5.3） |
| S-C8、S-X3 | 設定の画面を Application と `NEW_TASK` で開く形は今のブリッジ（`currentActivity` から開く）と違う | 両方 | 前面の Activity から開く（5.8） |
| S-C9 | 「要求できない」は Application の Context では判定できない | Claude | Application で判定するのは「API 32 以下」と「許可済み」だけ（5.8、K-6） |
| S-X2 | Share の前面の判定が 1b の「動作を変えない」と食い違う | Codex | 前面の判定は C ABI の受け口（2b）が行い、1b の既存の API は変えない（4.1、5.8、K-9、C-4） |
| R-X7（残り）、S-C14 | README D-6 の本文が古い | 両方 | README D-6 を直した |

## 総合評価

第 2 版は、文字列、コールバックの引数、システムコード、版、R8、プロセスの終わりを閉じた（両方）。残った A は 3 つの塊（登録の状態機械、初期化の状態機械、前面と Context の表）に集まっていた。状態機械の指摘が 2 回続いたので、第 3 版は 2 つの状態機械を「状態 × 出来事 → 振る舞い」の表で書き直し、`release` を呼ぶ所を 1 か所にした。新しい区分 A は 12 件（Claude 9、Codex 3）、B は 5 件、C は 4 件。3 回目のレビューで、A が 0 になったかを確かめる。
