## 仕組みの直し（同じ種類の指摘が続いたため）

v1 の A-1 と v2 の A-N1・A-N2・A-10 は、どれも「**テストのコードの書き方で、実機で許可の無い操作が起きないことを保証しようとして、穴が見つかる**」という同じ種類である。基底の `setUp` を通らないクラス、識別子の文字列を直接書く操作、`XCTFail` の後も続く処理、Swift にフォルダー単位の公開範囲が無いこと、とふさいでも次の穴が出る。review-document の「同じ種類の指摘が続いたら、それを生む仕組みを直す」に従い、守り方を次のように変える。

1. **一段目（主）: 実機で流すテストはランナーが決める**。`test_ios.sh` が、宣言の表（テスト名 → 要る区分）と `--device-allow` から、流してよいテストの一覧を作り、`-only-testing` で渡したものだけを流す。表に無いテストと、許されていない区分を要るテストは、**実機では起動しない**。テストのコードに穴があっても、許されていないテストのコードは実機で動かない
2. **二段目（補）: テストの中の確かめ**。基底の `setUpWithError` で `continueAfterFailure = false`、表を引いて許されていなければ throw する。印の型と発行の口は 1 ファイルの `fileprivate` にする。二段目は宣言の誤り（宣言より多くを触るテスト）を実行時に見つけるためのもので、一段目が守りの本体
3. 宣言の表は 1 か所（テストのターゲットの中の 1 ファイル）に置き、ランナーはそれを読む（ビルドしたものから `-enumerate-tests` で全テストを導き、表と完全に一致することを照らす。表に無いテストがあればランナーが止まる）
4. ソースの検査は、宣言の誤りの見逃しを減らす補助にとどめる

## 指摘と対応

### 区分 A

| ID | 出典 | 指摘 | 対応 |
|---|---|---|---|
| A-N1 | Claude | 今の `ClipboardUITests` と雛形の 2 クラスは自分の `setUpWithError` で `super` を呼ばずに `app.launch()` するので、基底の宣言の表・監視・縦向きが走らない | 一段目（ランナー）で実機では許されないかぎり起動しない。二段目として、基底の `setUpWithError` を `final` にし、子は別の口（`setUpAfterGate()`）を使う。既存の 3 クラスの setUp を書き換えると明記し、変異「子が評価を外す」を足す |
| A-N2 | Claude | 識別子の文字列を直接書く・ラベルで押す・`XCUIApplication(bundleIdentifier:` を書くと、印なしにシートや springboard を操作でき、grep を素通りする | 一段目で守る。二段目として、テストのクラスに `XCUIApplication` を持たせず `SampleApp` の private にする。grep は補助 |
| A-1（残り） | Codex | U10a の `press(.home)` を例外にしたので、宣言から `systemui` を消しても落ちない。今の Clipboard は印の口を通らない | 一段目で守る（U10a は宣言の表で `systemui` + `clipboard`）。例外は出現の回数も照らす（B-N5） |
| A-10 | Codex | 「表に無いテストは失敗」だけでは、`XCTFail` の後も処理と印の発行が続く実装ができる | 二段目を fail-closed にする: `continueAfterFailure = false`、`self.name` を正規化して表を引く、未登録は通常の Error を throw、許されていなければ `XCTSkip` を throw、印の口は `throws` で失敗のときは返さない、印の init は `fileprivate` |
| A-11 | Codex | 監視は UI が現れたときでなく、次の操作を妨げたときに呼ばれる。`false` は既定のハンドラに渡すので、バナーに誰も触らない保証にならない。未知のアラートの分岐の戻り値も書かれていない | 実機では、(a) 既知のアラートで否定のボタンがちょうど 1 つなら押して失敗を記録し `true`、(b) 未知のアラートやアラートでない割り込みは、ラベルを読まずに terminate し、失敗を記録して `true`。システムの UI を起こしうる操作の後には、明示のアラートの確かめを入れる。バナーが監視に来るかは 0c の最初に確かめる |
| A-12 | Codex | サンプルは `setup()` で delegate を入れた後に受け手を設定するので、その間に来たコールドスタートの応答が入れ物に届かない余地がある | 受け手を設定してから、最後に `setup()` を呼ぶ |
| A-13 | Codex | 6.3 の手順 0 でビルドしたものから列挙するのに、ビルドは手順 2 | `build-for-testing` の直後に `-enumerate-tests` と宣言の表の照合を行う |
| A-14 | Codex | 実機の `.xcresult` から添付を書き出すと、自動のスクリーンショットなどの写しが残りうる | 実機では添付を一切書き出さない。`tests/summary` の JSON だけを読んで `.xcresult` を消す。押したボタンの記録の取り出しはシミュレーターだけ |
