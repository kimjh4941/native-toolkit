## 基準を疑う: 何から守るか

v1〜v5 の 5 回、私物の端末を守る仕組みへの区分 A が続いた。v5 の A-23（`Support/` の補助のファイルに、許可の確かめの無い危ない関数を足せる）も同じ種類である。テストのコードを書く人が、守りを破る書き方をすることまで静的な検査で防ごうとすると、検査する範囲を広げるたびに、その外側に次の抜け道が見つかる。

そこで、守りの前提（脅威の範囲）を設計書に明記する。

- **守る相手**: エージェントと開発者の**うっかりした誤り**（宣言の付け忘れ、区分の書き誤り、補助を使わない直書き、継承や `#if` での思わぬ動き、許可の使い回し）。わざと守りを破るコードは対象外とする
- **信頼する部分**: 基底のファイルと `Support/` の決まったファイル（印の発行、`SampleApp`、springboard と Share のシートの操作、監視）は「信頼する部分」とし、中身をハッシュで固定する。変わったら、ランナーは実機で流さず、利用者に許可を求めるときに「信頼する部分が変わった」と示す。信頼する部分の変更は、別のモデルのレビューを通してからハッシュを更新する
- **最終の守り**: 実機で流すたびに、流すテストの名前と区分の一覧を利用者に見せて許可を得る（使い回せない形。A-24）

この前提の下で、v5 の指摘はすべて閉じる。

## 指摘と対応

### 区分 A

| ID | 出典 | 指摘 | 対応 |
|---|---|---|---|
| A-1v5 | Claude | NP1・NP2・CB1・CB2 は監視をテスト単位で外すので、関係の無い私物のアラートが次の操作を妨げると、XCTest の既定のハンドラがそのボタンを押しうる | この 4 件も監視を外さず、「何も押さない」監視を付ける（どの割り込みでも terminate し、印を立てて `true` を返す）。期待するダイアログは springboard で明示して待って押す（springboard の要素の操作は監視を起こさない） |
| A-22 | Codex | 実機の `.xctest` を `otool -ov` で見ると、`func testU1_...() throws` は `testU1_...AndReturnError:` の selector で現れる（Xcode 26.3 で確かめた）。「`test` で始まる引数の無いメソッド」の条件では拾えない | テストの宣言の形を `func test...()` と `func test...() throws`（同期）に限る（閉じた形の規則に足す。`async` のテストは禁じる）。selector の `test...AndReturnError:` を `test...()` に、`test...` を `test...()` に正規化する仕様と、実物を写した fixture での単体テストを書く。クラスと selector の対応は `otool -ov` で読む |
| A-23 | Codex | 閉じた形の規則は、許された `Support/` のファイルの中身と公開の口を固定も検査もしない。`SampleApp` に印の要らない危ない関数を足すと、テストの側には何も現れず、すべての照合を通る | 上の「信頼する部分」。基底と `Support/` の決まったファイルの中身をハッシュで固定し、変わったら実機で流さない。許可を求めるときに示す。更新は別のモデルのレビューの後 |
| A-24 | Codex | 同じコミット・作業ツリー・区分なら、前の `--approved` のファイルを何度でも使える。「毎回許可を得る」を強制できない | dry-run ごとにランダムな許可の ID を一覧に入れる。実機に触れる前に、使った ID を消費済みの台帳（リポジトリの外の決まった場所）に記録し、同じ ID の再利用を拒む。失敗の後の流し直しにも新しい許可を求める |
